How the modules depend on each other

An arrow points from the module that imports to the module that it imports. The width of an arrow shows the count of import statements. The box size shows the lines of code.

The only cycle: core ↔ billing. Core imports billing 4 times, and billing imports core 22 times. Core is the base that api, auth, billing and jobs build on. With this loop, a change in billing can reach every module that imports core.

Remove the 4 imports from core to billing to make the graph a clean set of layers. Move the shared types into core or shared, or invert the call with an interface.

Core carries the most load. Four modules import core, with 81 import statements in total. Treat its public interface as a contract during the refactor.

The heaviest edge is web → shared (58 imports). Web uses no other module, so web and shared form a separate front-end group.

Infra has no import edges. It is Terraform and you can refactor it on its own.

Start with these five files. They have 3,325 lines, and they had 60 commits in 90 days. Split each one along its busiest seams first.

Billing has small files with very high churn. billing/handlers/f01.go (34 commits), billing/service/f02.go (33) and billing/views/f00.go (28) are small, but each one changes about every three days. They show unstable logic, not files that are too big.

Four large files did not change. jobs/util/f02.py, core/model/f05.go, web/tasks/f16.tsx and jobs/model/f06.py each have more than 700 lines and 0 or 1 commits. They are stable, so they have low priority.
