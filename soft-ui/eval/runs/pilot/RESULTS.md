## R1-probe

**Judge:** Page A serves the 5-minute triage better. Its compact table and severity-coloured heatmap show how bad things are and where they cluster on one screen, and the repro steps open on demand. Page B holds the same facts but puts all 14 repro blocks open in a long scroll, and its heatmap and chart colours do not show severity the way the brief asks.

Only in the soft-ui page: A 'Flows probed: 5' stat tile that names the flows; Free-text search box above the filter chips; Findings shown as cards grouped under severity headers (critical, high, medium, low), with the evidence line and the numbered repro steps always open as code blocks; Heatmap shaded by count only, with no totals and no severity signal; The stacked bar colours do not match the severity chips (critical is blue in the chart and red in the list), which weakens the severity emphasis.

Only in the bespoke page: Heatmap cells coloured by the worst severity in the cell, so the flow x kind grid also shows where the critical findings sit, with row and column totals; Click a heatmap cell to filter the list; Callout notes that 3 security issues span checkout, cart and account; Raw-to-verified funnel in the header (31 raw findings to 14 verified, 25 probes over 5 flows); Compact one-row-per-finding table (ID, severity, title, flow, kind, file) with repro and evidence folded into expandable rows and an 'Expand all' control; Counts on each filter chip and a 'Showing N of 14' count.

**Soft-ui agent:** 4 render runs, 0 fixed lines, 2 error lines.

**Friction:** 1) A section that held a filter and a list failed with a JavaScript error: "Cannot read properties of undefined (reading 'forEach')". It failed both in the form that `explain section` shows (title + items inside the section) and with title as a sibling key. The error message was a raw JS exception, not a hint about how to fix the spec. Render printed no "fixed" line for it. I worked around it by putting the filter (with title "Findings") and the list at the top level. The heading-plus-grouped-list structure I wanted survives, but not as a real section. 2) When the stacked chart's series is severity, the colours come from a categorical palette (critical=blue, high=orange, medium=green, low=yellow). They do not use the severity tones that the list and filter chips use (critical/high red, medium amber, low blue). So the chart's colours contradict the rest of the page, and nothing in the spec maps series values to tones. 3) The stat tiles are hard-coded counts. stats from `data` gives one tile per row, so I found no way to get counts by severity from the findings dataset, and the tiles do not follow the filter bar. 4) An unquoted comma inside a YAML flow mapping (sub: browse, search, ...) silently cut the text to "browse". Render reported no warning, so I only found it on the screenshot. 5) I found no way to order the list groups or chart stacks by severity rank; they came out in the right order here, but only by luck of the data order. 6) The catalog does not say whether a filter bar also filters the chart and the heatmap. 7) A note for the harness: the first render run accidentally copied findings.json and run.json into the output folder. I deleted them, and the spec references ../../../reports/R1-probe/findings.json. run.json facts went into meta/stats by hand, because I found no easy way to bind a single-object JSON to kv.

## R3-design

**Judge:** Both pages use the same sections in the same order: stats, the call graph beside a component table, the sequence diagram, the data contracts, then the change simulation with a callout. Page B serves the review better: its layered graph, numbered flow and contract-usage notes make the design easier to follow, and it presents the retry exception and the low-volatility tension as open points to discuss, where page A presents the 6/7 result as a green success.

Only in the soft-ui page: Stat card for high-volatility parts (3) that names NotificationManager, PreferenceEngine and ChannelAccess; Component table grouped by kind, with collapsible group headers and counts; Data contracts drawn as a class diagram with relation arrows (Message -> Event, DeliveryResult -> Message); Bars for components_touched in the change table, sorted so the exception comes first; Meta chips under the title (8 components, 8 calls, 4 contracts, 7 simulated changes).

Only in the bespoke page: Call graph drawn in kind layers (Client, Manager, Engines, ResourceAccess/Utility), with a legend and volatility dots on each node; Stat that says the call edges are 'all one-way down'; 'Changes' column in the component table: how many simulated changes land in each component; Numbered steps on the sequence diagram, plus a numbered prose list of the 9 steps; For each data contract, where it is used (for example 'returned by PreferenceEngine.decide', 'in deliver(msg), record(msg)'); 'Kind' column in the change-simulation table, and the exception row highlighted; A warning-tone 'For discussion' callout: the retry change touches a second component that the design does not name, and 'Move user prefs' lands in UserDirectory, which the design rates low volatility; A claim that every high-volatility component absorbs at least one change.

**Soft-ui agent:** 8 render runs, 0 fixed lines, 29 error lines.

**Friction:** The final page renders with "check ok". The spec is /home/user/pskills/soft-ui/eval/runs/pilot/R3-design/tool.yaml. Layout: 4 stat tiles; "Shape of the system" (graph of the call edges beside a components table grouped by kind, volatility toned); the core use case as a Mermaid sequence diagram; then data contracts (Mermaid class diagram) beside the change simulation (table with bar, plus a good-tone callout).

Problems found:
1. The tool cannot select a key inside a nested JSON file. design.json is one object that holds 5 arrays. Loading it as a file gives key/value rows. I tried "file.json#key" and "dataset.key" and neither works. Neither catalog nor explain says how to pick a sub-array, and there is no "explain data". So I copied 3 arrays into the spec as inline CSV, which breaks the "give the path, do not copy data" rule. The spec grew to about 4.3k characters. A `path`/`key` option (for example `{file: design.json, key: components}` or `design.json#components`) would fix this. This is likely the most common case for the output of other skills.
2. `section` is broken at runtime. Every section, including the exact form in `explain section` and a minimal 1-text section, throws "Cannot read properties of undefined (reading 'forEach')" in the browser check. Static validation passes it. I used `col` with a `title` instead, which looks the same.
3. One static error was misleading: "row needs `items` (nodes)" appeared for a valid row when its child graph had a bad dataset. It is a cascade error that points at the wrong node.
4. A YAML trap that the tool did not catch: an unquoted comma list inside a flow mapping (`sub: A, B, C`) dropped silently to "A". I found it only in the screenshot. A warning for unknown keys in a flow mapping would catch it.
5. Missing features: no component makes a class or ER diagram, or a sequence diagram, from data. Contracts (type plus fields list) and core_use_case steps had to be hand-written as Mermaid. A `contracts`/`schema` component (types with field lists) and a `sequence` from rows (from, to, msg) would keep the data in the file. The `graph` component cannot colour or group nodes by a column of a second dataset (component kind/volatility), so the call graph does not show the Manager/Engine/ResourceAccess layering or the high-volatility parts. The graph also draws small at half width. No props let the tiles count values from the data (I typed 8/3/6/4 by hand).
6. None of the render output had a "fixed" line.

## R5-pr

**Judge:** Both pages give the same flow: the verdict and summary, then severity counts, files changed next to the findings ranked by severity, then the full diff with each finding inline at its line. Page A serves the author a little better. Its inline comments carry the finding IDs, and its files table shows which findings fall in each file, so the author can link the overview to the code faster. Page B leaves out the total line counts, and it shows files before findings.

Only in the soft-ui page: Separate stat tiles for each severity (high 1, medium 2, low 2), with colour accents; Split (side-by-side) diff view, not unified; Syntax highlighting and intra-line change highlighting in the diff; Note count for each file in the diff file headers ('2 notes'); Findings shown as a sortable table with separate file and line columns.

Only in the bespoke page: Total line count (+34 -4) and a commits count in the stat tiles; Finding IDs (C1-C5) on the inline review comments in the diff, so each comment links back to the findings list; Finding chips for each file in the files-changed table, and in each diff file header; Change bar in the files table shows added and removed lines (green and red); Findings list shows file:line under each title as one compact reference.

**Soft-ui agent:** 3 render runs, 0 fixed lines, 0 error lines.

**Friction:** All three renders printed "check ok", but that check missed two layout problems that I found only in the --shot screenshot. (1) With `sort: -severity`, the table sorted severity as plain text, descending, so the order was low, low, medium, medium, high. Tone colours already treat high/medium/low as an ordered scale, so I expected sorting to do the same. Plain `sort: severity` (ascending) did give high, medium, low, but `explain table` does not say that severity sorts by rank, so I had to guess. (2) The files table had 4 columns, two of them with inline bars, in a narrow row cell. The 'removed' column was cut off at the right edge, and the check still passed. I fixed it by dropping the status column and the second bar. Missing: nothing gives per-file added/removed counts as data, even though the diff component works them out for its own file headers (+8 -4). So I counted the lines in pr.diff by hand and typed them into an inline 'files' dataset. That is error-prone: the tests hunk header says +12, but the diff shows only 10 added lines. A `diff` option for a file summary, or a derived dataset such as `files: {from: pr.diff}`, would remove this step. pr.json is a single object, so I could not bind the callout text or the subtitle to its fields. I copied the verdict, summary, author, branch and commit count into the spec by hand, which breaks the 'do not copy data into the spec' rule. A `kv` could show them, but the callout and the subtitle cannot read fields from a dataset. In the diff, the review notes appear in code order, not severity order, which suits the brief's 'next to the code'. The findings table shows the severity order. Clicking a finding row does not jump to its note in the diff. I wanted that link but found no prop for it.
