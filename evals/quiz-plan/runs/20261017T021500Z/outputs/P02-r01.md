## Intent

Today `orders.status` is free text. Typos such as `shiped` and `canceled` get in. The same status then appears under two spellings, and the dashboard's per-status counts come out wrong.

When this plan is done, `orders.status` is a Postgres enum with five values: `pending`, `paid`, `shipped`, `cancelled`, and `refunded`. The database rejects any other value. The migration fixes the two known typos in existing rows: `shiped` becomes `shipped` and `canceled` becomes `cancelled`. Any other unknown value makes the migration fail. The migration does not guess.

The dashboard's per-status counts must match a `SELECT status, count(*) FROM orders GROUP BY status` taken before the migration (the baseline). The typo rows are folded into their fixed values. To fold means to add the count of `shiped` to `shipped` and the count of `canceled` to `cancelled`.

The public REST API keeps its JSON shape. Nothing in `src/payments/` changes.

**Not doing:**

- Any change to the JSON shape of the public REST API.

## Approach

**Chosen:** one Knex migration in `db/migrations/` creates a native Postgres enum type (assumed name: `order_status`) with the five values.
