# CAP-store · Keep items in a file

Status: active

## What it is for

It keeps the to-do items in a text file, one item on each line. It gives them back in the order in which they were added. Jobs use it to load the items, to add one, and to mark one as done. Each item has a done state that stays in the file.

## Code map

- src/store.rs

## Interface

- `Store::new(path: impl Into<PathBuf>) -> Store` · call · `src/store.rs`
  - in: file path
  - out: a Store for that path, which does not touch the file
  - errors: none
- `Store::load(&self) -> io::Result<Vec<Item>>` · call · `src/store.rs`
  - in: nothing
  - out: items in added order, each with its done state, and an empty list if the file is missing
  - errors: the `io::Error` from any read failure except not-found

## Requirements

### CAP-store.R1 · Load returns items in added order

Status: ready · Intents: IN-0001

Loading gives every stored item in file order, which is the order of adding. Each item has its done state. A missing file gives an empty list.

- Given a file with lines `1<TAB>a` and `2<TAB>b`, when load is called, then it returns items 1 "a" and 2 "b" in that order.
- Given no file at the path, when load is called, then it returns an empty list and no error.

### CAP-store.R2 · Load skips malformed lines

Status: built · Intents: none · Source: recon

Lines without a tab, or with an id that is not an unsigned integer, are left out without an error. Text after the first tab is kept whole.

- Given a line with no tab or a non-numeric id, when load is called, then that line is missing from the result.
- Given a line `3<TAB>a<TAB>b`, when load is called, then the item text is `a<TAB>b`.

### CAP-store.R3 · Load passes on read errors

Status: built · Intents: none · Source: recon

Any read failure other than a missing file comes back as the I/O error. Non-UTF-8 content also fails this way.

- Given an unreadable path, when load is called, then it returns the I/O error.

### CAP-store.R4 · Add assigns the next id (highest id plus one)

Status: built · Intents: none · Source: recon

Adding gives the new item an id one higher than the highest stored id. The first item gets id 1. The new item goes last.

- Given an empty store, when add("x") is called, then it returns id 1.
- Given stored ids 1 and 5, when add is called, then the new id is 6.

### CAP-store.R5 · Add replaces tabs and line breaks with spaces

Status: built · Intents: none · Source: recon

Each tab, newline, and carriage return in the text becomes one space. The returned item holds the changed text. Other text is kept as given.

- Given text "a<TAB>b\nc", when add is called, then the item text is "a b c".

### CAP-store.R6 · Add writes the whole file

Status: built · Intents: none · Source: recon

Each add rewrites the file with all loaded items plus the new one. This creates the file if it is missing. Malformed lines drop out of the file on the next add. The parent folder must exist.

- Given a missing file, when add is called, then the file exists after and holds one line.
- Given a file with a malformed line, when add is called, then that line is gone from the file.

### CAP-store.R7 · Add passes on I/O errors

Status: built · Intents: none · Source: recon

If load or write fails, add returns the I/O error and gives no item.

- Given an unwritable path, when add is called, then it returns the I/O error.

### CAP-store.R8 · An item has a done state

Status: ready · Intents: IN-0001

Each item is done or not done. A new item is not done. The file holds the state, so a new Store on the same file sees it. A done item has `*` right after its id, and a tab, and then the text (assumed).

- Given a store with a new item, when load is called, then the item is not done.
- Given a done item, when a new Store opens the same file and loads, then the item is done.
- Given a done item, when add is called, then the done item stays done in the file.

### CAP-store.R9 · Mark an item as done

Status: ready · Intents: IN-0001

Marking an item gives it the done state and saves the file. Marking an item that is done already changes nothing (assumed). An id with no item changes nothing and gives false.

- Given items 1 and 2, when mark_done(2) is called, then item 2 is done and item 1 is not done.
- Given item 2 is done, when mark_done(2) is called, then the call gives true and item 2 stays done.
- Given items 1 and 2, when mark_done(7) is called, then the call gives false and no item changes.

### CAP-store.R10 · A file from before the done state loads as not done

Status: ready · Intents: IN-0001

A data file with lines of the form `<id><TAB><text>` still loads. Each of its items is not done. This line is a stored-data line.

- Given a file with lines `1<TAB>milk` and `2<TAB>eggs`, when load is called, then items 1 and 2 are not done.
- Given that file, when mark_done(1) is called, then item 1 is done and item 2 is not done.

# DES-pdlc-check-tagging · How checks name their requirement

Status: agreed · Default: yes

## Rule

The requirement ID starts the name of the check, for example `CAP-email.R3 sends from a
template`. A check that proves two requirements names the two requirements.

If the check runner does not accept `.` or `-` in names (Python's `unittest`, for
example), write the ID with underscores instead: `test_CAP_email_R3_sends_from_a_template`.
The two forms count as the same ID. Use only one form in each project.

Lay checks out the same way everywhere:

- Put new check files in the check folder (`tests/` in a project that had none). Name
  each file after the spec it proves, in a form the runner finds: `test_CAP_email.py`,
  `CAP-email.test.js`.
- Inside a file, make one group per requirement (a test class or a `describe` block).
  Name the group with the requirement ID: `class CAP_email_R3(unittest.TestCase)`,
  `describe("CAP-email.R3", ...)`.
- Each check's name still starts with the ID, then says what it proves.

The acceptance checks of an intent go in one file for each intent, at the path of
"acceptance file" in `pdlc/config.md`. The name of the file holds the word "acceptance"
and the intent ID, for example `tests/acceptance_IN_0012.py` or
`acceptance/IN-0012.acceptance.js`. The "all" command does not run such a file. Inside the
file, make one group for each requirement, and start each check name with the requirement
ID.

## Why

The trace from a requirement to its checks is only as good as this naming. Thus, the
naming must be simple and the same everywhere.

# DES-errors · The project's error codes

Status: agreed · Default: yes

## Rule

Each error that the system can give has a code here, in `UPPER_SNAKE_CASE`. Acceptance
lines, Interface entries, and checks all use these codes. Thus, a check can expect the
exact error.

| Code | Meaning | Whose fault | Retry helps? |
|---|---|---|---|
| `ITEM_NOT_FOUND` (assumed) | The id in the request matches no item. | caller | no |

When a requirement needs a new error, add a row. When the meaning is the same, use the
existing code again.

Add rows at intake and ready. Do not add a row while a change is in tests, build, or
verify. When you add a row, leave `Default:` as it is. Write each row the same way:

- The code in backticks.
- "Whose fault": `caller`, `system`, or `outside service`.
- "Retry helps?": `yes` or `no`.

Checks and the code of the app match on the error code. Each requirement decides what a
person sees, for example a message or a status. The message or the status can omit the
error code. If the caller cannot see the error code, a check expects the exact message and
status instead.

## Why

A check that expects "an error" passes for any error, also for a typo. A named code makes
the check exact. A named code also gives callers a stable value to handle.

# CAP-store · Keep items in a file

Status: active

## What it is for

It keeps the to-do items in a text file, one item on each line. It gives them back in the order in which they were added. Jobs use it to load the items, to add one, and to mark one as done. Each item has a done state that stays in the file.

## Code map

- src/store.rs

## Interface

- `Store::new(path: impl Into<PathBuf>) -> Store` · call · `src/store.rs`
  - in: file path
  - out: a Store for that path, which does not touch the file
  - errors: none
- `Store::load(&self) -> io::Result<Vec<Item>>` · call · `src/store.rs`
  - in: nothing
  - out: items in added order, each with its done state, and an empty list if the file is missing
  - errors: the `io::Error` from any read failure except not-found
- `Store::add(&self, text: &str) -> io::Result<Item>` · call · `src/store.rs`
  - in: item text
  - out: the new `Item`, with its id, its cleaned text, and `done` false
  - errors: the `io::Error` from load or write
- `Store::mark_done(&self, id: u64) -> io::Result<bool>` · call · `src/store.rs` · proposed
  - in: the id of an item
  - out: true if an item with that id exists, which is done after the call, and false if no item has that id
  - errors: the `io::Error` from load or write

  - in: not applicable

  - errors: none

## The requirements, in full

### CAP-store.R1 · Load returns items in added order

Status: ready · Intents: IN-0001

Loading gives every stored item in file order, which is the order of adding. Each item has its done state. A missing file gives an empty list.

- Given a file with lines `1<TAB>a` and `2<TAB>b`, when load is called, then it returns items 1 "a" and 2 "b" in that order.
- Given no file at the path, when load is called, then it returns an empty list and no error.

### CAP-store.R8 · An item has a done state

Status: ready · Intents: IN-0001

Each item is done or not done. A new item is not done. The file holds the state, so a new Store on the same file sees it. A done item has `*` right after its id, and a tab, and then the text (assumed).

- Given a store with a new item, when load is called, then the item is not done.
- Given a done item, when a new Store opens the same file and loads, then the item is done.
- Given a done item, when add is called, then the done item stays done in the file.

### CAP-store.R9 · Mark an item as done

Status: ready · Intents: IN-0001

Marking an item gives it the done state and saves the file. Marking an item that is done already changes nothing (assumed). An id with no item changes nothing and gives false.

- Given items 1 and 2, when mark_done(2) is called, then item 2 is done and item 1 is not done.
- Given item 2 is done, when mark_done(2) is called, then the call gives true and item 2 stays done.
- Given items 1 and 2, when mark_done(7) is called, then the call gives false and no item changes.

### CAP-store.R10 · A file from before the done state loads as not done

Status: ready · Intents: IN-0001

A data file with lines of the form `<id><TAB><text>` still loads. Each of its items is not done. This line is a stored-data line.

- Given a file with lines `1<TAB>milk` and `2<TAB>eggs`, when load is called, then items 1 and 2 are not done.
- Given that file, when mark_done(1) is called, then item 1 is done and item 2 is not done.

# DES-pdlc-check-tagging · How checks name their requirement

Status: agreed · Default: yes

## Rule

The requirement ID starts the name of the check, for example `CAP-email.R3 sends from a

The two forms count as the same ID. Use only one form in each project.

Lay checks out the same way everywhere:

- Put new check files in the check folder (`tests/` in a project that had none). Name
  each file after the spec it proves, in a form the runner finds: `test_CAP_email.py`,
  `CAP-email.test.js`.
- Inside a file, make one group per requirement (a test class or a `describe` block).
  Name the group with the requirement ID: `class CAP_email_R3(unittest.TestCase)`,
  `describe("CAP-email.R3", ...)`.
- Each check's name still starts with the ID, then says what it proves.

The acceptance checks of an intent go in one file for each intent, at the path of
"acceptance file" in `pdlc/config.md`. The name of the file holds the word "acceptance"
and the intent ID, for example `tests/acceptance_IN_0012.py` or

naming must be simple and the same everywhere.
